# dsh-connect-raccoon 的架构决策（ADR）

> 本文件记录**为什么这样实现**，不是功能说明。功能说明在 `README.md`，
> 上游协议取证在 `docs/PROTOCOL.md`、`docs/WEB-LOGIN.md`、`docs/DESKTOP-CREDS.md`。
> 每一条决策都带「代价」，因为不带代价的决策无法被复核。

---

## ADR-1：凭据来源两条腿，账户池是**插件自己**的容器

**决策**：账号只来自两个地方 —— ①本机小浣熊桌面端的 `~/.box-agent/config/auth.json`（只读复用）；
②插件自己的授码/扫码登录。**账户池是插件自己的目录**（`$DSH_HOME/raccoon-vault/accounts/<id>.json`），
不是「把客户端的多个账号读出来」。

**为什么**：桌面端一个 `auth.json` 只承载一份登录态，上游 `account-store` 给 Raccoon 的也是单值槽。
「客户端有多个账号」这条路在数据模型上不存在（`docs/DESKTOP-CREDS.md` §3 三证据）。

**代价**：客户端里那一个账号只能贡献池里一个成员；想要第二个账号必须走网页/扫码登录。
界面必须把这一点说出来，否则用户会以为「装了两个客户端账号就应该出现两行」。

## ADR-2：桌面端文件**默认只读**，只在轮转时写回，且必须单飞

**决策**：
- token 未临近过期 → 一个字节都不写、一个请求都不发。
- 临近过期（余量 5 分钟）→ 刷新一次，**串行**（同一账号全局单飞），把轮转后的对**原子写回**
  App 自己的 `auth.json`（临时文件 + rename，保 5 键原序）。
- 每次进程**首次**写回前，先在 `$DSH_HOME` 留一份被替换文件的备份。

**为什么**：小浣熊的 refresh 是单次使用（换一次，新旧一起轮转）。只读不写回 → App 下次拿旧
refresh token 去换会 `refresh_conflict`，用户被登出；并发刷新 → 两次用同一 refresh token，必然废掉一个。

**代价**：写回是**对另一个程序的文件写**。App 升级改了键序或加了字段时，必须保未知字段 + 保序，
否则会在 App 侧产生无意义 diff。任何「保字段失败」都按失败处理（宁可不写回、报错让用户重开 App），
不做「尽力而为的半份”。

## ADR-3：网页登录主线是 **loopback 授权回调**，扫码是快路径，手粘 code 是兜底

**决策**：
1. 主路径：本地 `listen(0,'127.0.0.1')` 起一个**只收一次回调**的服务器 → 拼
   `https://xiaohuanxiong.com/authorize?...&desktop_callback=loopback&redirect=http://127.0.0.1:<port>/auth/callback`
   → 用户在浏览器里登录 → 浏览器 `location.assign` 到回环地址 → 插件收 `code` → 换 token 对。
2. 快路径：`POST /api/iam/v1/auth/mp/qrcode`（微信小程序扫码），纯 HTTP 可驱动，但**拿不到 refresh_token**。
3. 兜底：手粘授权码（整条回调 URL 或裸码），`state` 逐字校验。

**为什么**：`desktop_callback=loopback` 是官方 SPA 给 IDE 插件准备的一等公民通道（证据见
`docs/WEB-LOGIN.md` §5.2，读自授权页 chunk `c8.js`）。它让「无需客户端、无需 DevTools」同时成立。
参考实现一直卡在手粘，是因为它用的 `state` 是 32 hex（UUID 去横线），授权页硬校验要求 **64 hex**。

**代价**：主线链路最后一跳（浏览器真的 assign 到 127.0.0.1）**未端到端实测**（需要真人登录）。
所以实现里保留手粘兜底；并且 `state` 必须逐字比对 —— 少了这一步，任何本地进程都能伪造一次登录。

## ADR-4：账户池 = 显式勾选的成员 + 失败依次换号，**排序不写回用户选择**

**决策**：
- 池成员**默认零个**，必须显式勾选（「本机有登录」≠「要拿它花钱」）。
- 池开关关着 → 永远用用户手选的那个账号。
- 池开关开着 → 每次请求按「可用优先 → 快过期先花 → 积分高 → 凭据新」排序挑一个；
  该请求失败时**依次换池内其他可用账号重试**；换号**不写回** `selected`。
- **请求本身不合法（HTTP 400）不换号**：同一个 body 换谁都是 400，重试只白等。

**为什么**：照 `dsh-connect-workbuddy` 已验证的形状。关键一条是「运行时借用 ≠ 篡改用户选择」——
否则关掉开关后用户看不到自己原来选的账号了。

**代价**：开着池时「卡片上显示的当前账号」与「本次实际计费账号」可能不同。因此界面必须同时显示
「当前选用」与「本次实际使用（含原因）」，不能只显示一个。

## ADR-5：用一个**只做转发与换号**的回环 shim，纯 OpenAI 直通

**决策**：`PiAiAdapter` → 本地回环 shim（`127.0.0.1:<随机端口>` + 进程内随机 secret）
→ 小浣熊 `https://xiaohuanxiong.com/api/web/llm/v2`。shim **不做协议翻译**（上游本来就是
OpenAI 兼容的，`delta.reasoning_content` 由 pi-ai 的 openai-completions 原生识别），
它只做三件 pi-ai 做不到的事。

**为什么必须要有这一层**（推翻「直连更简单」的初判）：
`PiAiAdapter.resolveApiKey` 在文档里写明「每个 stream 调用解析一次并**为该调用冻结**」。
也就是说 pi-ai 侧一个请求只有一个身份，它的重试是「同一个身份再发一次」。
换号这件事必须在**发出请求之前**、在**收到第一个字节之前**改变身份 —— pi-ai 没有这个钩子
（`Model` / `Provider` 只接受静态 headers，不接受自定义 fetch）。

**代价**：多一个监听端口、多一个「流掉了」的故障面。所以 shim 被刻意压到最小：
不做协议转换、不做重试策略（重试只发生在换号时，且只在零字节阶段）、不缓存任何正文。
它的正确性由「并发上限 + 零字节判定 + 首字节后只透传」三条钉住。

## ADR-6：换号只发生在「尚未吐出任何字节」之前

**决策**：shim 里先按池排序取候选账号，逐个尝试。判定为**可换号**的失败只有四类：
`401/403`（令牌失效）、`429` 或 `user_model_rate_limited`（限流）、积分耗尽、
上游 `5xx`。判定为**不可换号**的立刻把上游原文返回给宿主：`400`（请求体非法，
换谁都是 400）、`404`（模型不存在）、以及任何**已经开始吐字节**之后的错误。

**为什么**：换号发生在流中途会让宿主收到两条拼接的回复 —— 比直接失败糟糕得多。
所以「是否已经往客户端写过字节」是硬判定，一旦写过，后续错误只能作为流内 error 帧上报。

**代价**：一次对话里不能在中途换号。长对话撞上某账号的吞吐墙时，只能整轮失败后由用户重发。
界面上要把「本次用的是哪个账号」显示出来，否则用户无从判断该不该换号。

## ADR-7：浏览器半边是手写经典脚本，且只读两条宿主路由

**决策**：`src/client/bundle.js` 是经典脚本（无 import/export），通过
`window.__ModuleLoader__.load({ id, factory })` 注册；数据只来自
`/plugins/dsh-connect-raccoon/{status,action}` 两条宿主路由。

**为什么**：进了打包器会打出第二份 React，hooks 立刻崩（全局规则）。token 绝不进页面 ——
页面拿到的只有脱敏的账号名、余额、到期时间与一次性登录会话状态。

**代价**：没有类型检查兜底，必须靠 `scripts/check-client.mjs` 静态自检（可解析 / 无模块语法 /
zh-en 同键 / `t()` 键都存在）。**账号 token 永远不出宿主进程**，代价是页面上任何需要 token 的
交互都得由宿主代为执行。

## ADR-8：失败原因说人话，上游错误码原样保留

**决策**：把上游业务码映射成可执行建议：

| 上游 | 插件说什么 |
| --- | --- |
| `200001 authorization_empty_error` | 没带登录令牌（编程错误，不是用户操作问题） |
| `200003 authorization_verify_error` | 登录态已失效 → 换号或重新登录 |
| `100002 params_invalid_error` | refresh_token 格式非法 → 重新登录 |
| `200035 authorization_code_not_found_error` | 授权码已用过/过期 → **不重试**，重新发起登录 |
| `AUTH_QRCODE_INVALID/EXPIRED/NOT_FOUND` | 二维码过期/无效 → 重新发起扫码 |
| `user_model_rate_limited` | 该模型吞吐被限（**不是**请求频率），上游不给 Retry-After |

**为什么**：`user_model_rate_limited` 的文案写的是「请求频率超限」，实测是**吞吐**墙
（十个大请求十秒内撞墙，五十个小请求不撞）。照抄文案会让用户去加 sleep，而正确动作是换小模型或等。

**代价**：映射表是硬编码的，上游加新码时会落到「未知错误：<原文>」分支 ——
我们宁可把原文交给用户，也不猜一个可能误导的语义。
